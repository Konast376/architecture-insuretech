# Task 1. Проектирование технологической архитектуры InsureTech

## 1. Исходные требования

| Требование                        | Принятое решение                                                                                                                                                                  |
|-----------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Доступность не ниже 99,9%         | Компоненты распределены по трём зонам доступности. Нет одиночных экземпляров критических сервисов.                                                                                |
| Работа 24/7                       | Региональный Kubernetes-кластер, автоматическое масштабирование, rolling update, PodDisruptionBudget, мониторинг и дежурная эскалация.                                            |
| RTO не более 45 минут             | Автоматический failover приложений и PostgreSQL выполняется без ручного восстановления. Для логических ошибок предусмотрен PITR и регулярно проверяемая процедура восстановления. |
| RPO не более 15 минут             | PostgreSQL использует кворумную синхронную репликацию между зонами. Для disaster recovery применяются архивы WAL и Point-in-Time Recovery.                                        |
| Рост нагрузки                     | Горизонтальное масштабирование pod и worker node. Вертикальное масштабирование остаётся вспомогательным способом для БД и отдельных узких мест.                                   |
| Стабильная загрузка страниц по РФ | Статические файлы отдаются через CDN из ближайшей точки присутствия. Каталог продуктов и тарифов кешируется.                                                                      |
| Объём данных 50 GB                | Шардирование не применяется. Оно увеличит сложность без измеримого выигрыша при данном объёме.                                                                                    |

## 2. Краткое описание решения

Публичный трафик входит через `Cloud DNS`. Статические файлы веб-приложения раздаются через `Cloud CDN`, а источником служит `Object Storage`. Динамические запросы сайта и B2B API проходят через `Smart Web Security`, затем через `Application Load Balancer` и попадают в региональный кластер `Managed Service for Kubernetes`.

Кластер Kubernetes имеет высокодоступный control plane и worker node groups в трёх зонах:

- `ru-central1-a`;
- `ru-central1-b`;
- `ru-central1-d`.

Каждый прикладной сервис развёрнут минимум в трёх экземплярах, по одному экземпляру в каждой зоне. Фактическое количество реплик увеличивается HPA, то есть Horizontal Pod Autoscaler, механизмом горизонтального автомасштабирования pod. Узлы Kubernetes масштабируются Cluster Autoscaler.

Данные хранятся в одном высокодоступном кластере Managed PostgreSQL с тремя хостами. Один хост выполняет роль master, два других являются репликами. Роль master может автоматически перейти на актуальную реплику. Для продуктов, тарифов и пользовательских сессий добавлен Redis-совместимый кеш Managed Valkey. Кеш не является источником истины: при его недоступности приложение обращается к PostgreSQL и внешним API.

## 3. Почему выбран один региональный Kubernetes-кластер

Выбран один региональный кластер с highly available master и node groups в трёх зонах, а не три независимых кластера.

Причины:

1. Региональный control plane продолжает работать при отказе одной зоны.
2. Kubernetes сохраняет единый service discovery, единые политики и один контур развёртывания.
3. Не требуется синхронизировать конфигурацию, секреты и релизы между тремя независимыми кластерами.
4. Балансировщик может направлять трафик только в доступные pod во всех зонах.
5. Такой вариант закрывает требование доступности 99,9% и отказ отдельной зоны с меньшей операционной сложностью.

Три независимых кластера были бы оправданы при развёртывании в нескольких географических регионах или у нескольких облачных провайдеров. В текущей схеме отказоустойчивость обеспечивается на уровне зон доступности одного российского региона Yandex Cloud.

## 4. Масштабирование

### 4.1. Горизонтальное масштабирование

Для прикладного слоя используется горизонтальное масштабирование:

- `core-app`, `client-info` и `ins-product-aggregator` работают как Kubernetes Deployment;
- минимальное количество реплик каждого критического Deployment равно трём;
- HPA увеличивает число pod по CPU, RPS, длине очереди и p95 latency;
- Cluster Autoscaler добавляет worker node при нехватке ресурсов;
- `topologySpreadConstraints` распределяет pod между зонами;
- `podAntiAffinity` не допускает размещение всех реплик на одном узле;
- `PodDisruptionBudget` сохраняет минимум две доступные реплики при обслуживании;
- для всех контейнеров задаются `requests` и `limits`.

Горизонтальное масштабирование выбрано основным, поскольку веб-запросы и API-запросы могут обрабатываться параллельно. Для этого состояние HTTP-сессии не должно храниться в памяти конкретного pod.

### 4.2. Вертикальное масштабирование

Вертикальное масштабирование применяется как вспомогательная мера:

- увеличение класса хостов PostgreSQL;
- увеличение CPU и RAM worker node для тяжёлых интеграционных операций;
- увеличение ресурсов отдельных pod после профилирования.

Вертикальное масштабирование ограничено размером одной машины и часто требует перезапуска. Поэтому оно не является основной стратегией для прикладных сервисов.

## 5. Балансировка нагрузки

### 5.1. Географическое распределение

`Cloud CDN` хранит копии статических файлов в точках присутствия и направляет пользователя к подходящей точке с учётом географической близости, загрузки и качества канала. Это снижает зависимость времени загрузки SPA, изображений, JavaScript и CSS от расстояния до центрального дата-центра.

Динамический API проходит через Application Load Balancer. Балансировщик распределяет запросы только между здоровыми endpoint Kubernetes в доступных зонах.

Важно: физически одинаковая задержка динамического API для всех регионов РФ не может быть гарантирована одним географическим регионом. Схема максимально снижает различия за счёт CDN, кеширования и оптимизации API. Для строгого требования одинакового RTT потребовалось бы несколько географически удалённых площадок или второй облачный провайдер.

### 5.2. Разделение B2C и B2B

На входе Smart Web Security применяются:

- WAF, то есть Web Application Firewall, фильтр атак прикладного уровня;
- защита от DDoS и ботов;
- Advanced Rate Limiter;
- отдельные лимиты и квоты по `partner_id` или API key.

Это не позволяет одному B2B-партнёру занять все ресурсы системы. В Kubernetes дополнительно можно разделить B2C и B2B ingress, задать отдельные HPA и resource quota.

## 6. Health checks

На схеме показаны четыре уровня проверок.

### 6.1. Application Load Balancer

Балансировщик проверяет endpoint `GET /health/ready`.

Рекомендуемая начальная конфигурация:

- интервал: 5 секунд;
- timeout: 2 секунды;
- healthy threshold: 2 успешные проверки;
- unhealthy threshold: 3 неуспешные проверки.

### 6.2. Kubernetes probes

Каждый сервис реализует:

- `/health/startup` для проверки завершения запуска;
- `/health/ready` для подтверждения готовности принимать трафик;
- `/health/live` для определения зависшего процесса.

Проверка liveness не должна зависеть от доступности страховых компаний. Иначе сбой внешнего API вызовет перезапуск всех pod и усилит инцидент. Состояние внешних зависимостей отображается отдельными метриками и учитывается в readiness только тогда, когда сервис действительно не может выполнить ни одну операцию.

### 6.3. Проверки базы данных

Приложение использует connection pooler. В мониторинг передаются:

- успешность подключения;
- время выполнения простого SQL-запроса;
- replication lag;
- количество активных соединений;
- использование CPU, RAM и диска;
- момент смены master.

### 6.4. Синтетические проверки

Внешний probe регулярно вызывает:

- публичный `/health`;
- загрузку главной страницы;
- поиск страхового продукта;
- тестовую безопасную операцию API без оформления реального договора.

Так команда узнаёт о недоступности до обращений пользователей.

## 7. Failover-стратегия

### 7.1. Отказ pod или worker node

1. Kubernetes прекращает направлять трафик в pod после провала readiness probe.
2. ReplicaSet создаёт замену.
3. Благодаря anti-affinity новая реплика размещается на другом узле.
4. Application Load Balancer продолжает работать с оставшимися endpoint.

Ожидаемый RTO: от нескольких секунд до нескольких минут. Потери данных отсутствуют, поскольку pod не хранит постоянное состояние.

### 7.2. Отказ зоны доступности

1. Health checks исключают endpoint отказавшей зоны.
2. Приложение продолжает работу в двух оставшихся зонах.
3. HPA и Cluster Autoscaler компенсируют потерянную вычислительную мощность.
4. При восстановлении зоны pod распределяются обратно с помощью topology spread.

Чтобы пережить отказ одной зоны без деградации ниже допустимого уровня, нормальная загрузка каждой зоны не должна превышать приблизительно 50% её доступной мощности. Это оставляет запас N+1.

### 7.3. Отказ master PostgreSQL

Managed PostgreSQL автоматически выбирает новую master-реплику. Кворумная синхронная репликация подтверждает транзакцию после записи WAL на master и кворум реплик. При стандартной настройке `synchronous_commit = on` это позволяет ориентироваться на RPO, близкий к нулю, для отказа одного хоста или зоны.

Приложение должно:

- использовать корректный FQDN или механизм обнаружения master;
- повторять только безопасные транзакции;
- ограничивать время ожидания соединения;
- очищать устаревшие соединения пула после failover.

### 7.4. Логическая ошибка или повреждение данных

Для восстановления используются:

- автоматические ежедневные backup;
- архивирование WAL;
- Point-in-Time Recovery;
- retention 30–60 дней;
- регулярные учения восстановления в отдельный кластер.

При объёме 50 GB восстановление необходимо проверять на практике. Для выполнения RTO 45 минут заранее резервируются квоты, описывается runbook и используется достаточное число CPU у восстанавливаемого кластера.

## 9. Конфигурация PostgreSQL

Предлагаемая топология:

- один Managed PostgreSQL cluster;
- три хоста в `ru-central1-a`, `ru-central1-b`, `ru-central1-d`;
- автоматическое управление потоками репликации;
- кворумная синхронная репликация;
- `synchronous_commit = on`;
- PgBouncer для контроля количества соединений;
- быстрые сетевые или SSD-диски;
- отдельные базы или схемы сервисов с раздельными пользователями и правами;
- автоматические backup;
- PITR включён;
- retention 30–60 дней;
- регулярное тестовое восстановление.

Отдельные read replicas могут использоваться для отчётности и некритичных запросов. Критические операции чтения после записи должны выполняться на master либо с настройкой, обеспечивающей требуемую согласованность.

## 10. Решение по шардированию

Шардирование не используется.

Причины:

1. Общий объём данных равен 50 GB и без проблем помещается в одном PostgreSQL cluster.
2. Шардирование усложняет транзакции, joins, миграции, резервное копирование и эксплуатацию.
3. Текущие проблемы связаны прежде всего с одиночной БД, отсутствием реплик, недостаточным масштабированием приложения и отсутствием кеширования.
4. Вертикальное масштабирование PostgreSQL, индексы, PgBouncer, кеш и read replicas имеют существенно меньшую стоимость внедрения.

Решение нужно пересмотреть, если:

- объём данных приблизится к сотням GB или TB;
- write throughput стабильно упрётся в предел одного master;
- IOPS дисковой подсистемы станет постоянным ограничением;
- появится естественный ключ разделения данных, например tenant или регион, и межшардовые транзакции будут редкими.

## 11. Поведение прикладных сервисов

### `core-app`

- разворачивается как stateless Deployment;
- минимум три реплики;
- состояние сессий вынесено в Valkey или подписанные stateless token;
- использует timeout и connection pool для внутренних вызовов.

### `client-info`

- минимум три реплики;
- персональные данные доступны только из private network;
- операции изменения выполняются транзакционно;
- права пользователя БД ограничены собственной схемой.

### `ins-product-aggregator`

- минимум три реплики;
- параллельно вызывает страховые компании;
- для каждого внешнего API настроены timeout, retry с exponential backoff и circuit breaker;
- частичные результаты допустимы, если бизнес-сценарий это разрешает;
- продуктовые данные кешируются.

### `ins-comp-settlement`

- запускается как Kubernetes CronJob;
- используется distributed lock, чтобы расчёт не выполнился одновременно в нескольких экземплярах;
- повторный запуск должен быть идемпотентным, то есть не создавать повторные начисления.

## 12. Мониторинг и реагирование

Используются:

- Yandex Monitoring для инфраструктурных и сервисных метрик;
- Managed Prometheus для Kubernetes и бизнес-метрик;
- Cloud Logging для централизованных логов;
- Audit Trails для административных событий;
- уведомления в Telegram, SMS и email;

Минимальные алерты:

- availability ниже SLO;
- рост HTTP 5xx;
- p95 и p99 latency выше порога;
- отсутствие healthy backend в одной или нескольких зонах;
- число доступных реплик ниже двух;
- HPA достиг максимума;
- worker nodes не масштабируются;
- replication lag;
- смена PostgreSQL master;
- диск PostgreSQL заполнен более чем на 80% и 90%;
- ошибка backup или слишком старый WAL archive;
- недоступность конкретной страховой компании;
- превышение квоты B2B-партнёром.
