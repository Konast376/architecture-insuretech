# Задание 4. Онлайн-оформление ОСАГО

## 1. Принятое архитектурное решение

Новая схема является развитием Event-Driven архитектуры из задания 3. Декомпозиция существующих сервисов сохраняется. Добавляется отдельный сервис `osago-aggregator`, его собственная база данных и инфраструктурный SSE-backplane для доставки уведомлений между несколькими экземплярами `core-app`.

Основной поток построен асинхронно:

1. Веб-приложение создаёт заявку через REST API `core-app`.
2. `core-app` сохраняет заявку и событие `OsagoApplicationRequested` в одной транзакции PostgreSQL с применением Transactional Outbox.
3. Outbox Relay публикует событие в Kafka.
4. Один из экземпляров `osago-aggregator` получает событие, создаёт заявки во всех страховых компаниях и опрашивает их REST API до получения решений либо до истечения общего срока 60 секунд.
5. Каждый полученный оффер и каждое терминальное состояние сохраняются в БД `osago-aggregator` вместе с записью outbox.
6. События `OsagoOfferReceived`, `OsagoInsurerFailed` и `OsagoSearchCompleted` передаются через Kafka в `core-app`.
7. `core-app` сохраняет оффер в своей БД и сразу передаёт уведомление в веб-приложение через Server-Sent Events, сокращённо SSE. SSE представляет собой постоянное однонаправленное HTTP-соединение от сервера к браузеру.

## 2. Требуется ли `osago-aggregator` собственное хранилище

Да, отдельное долговременное хранилище необходимо. Рекомендуется PostgreSQL, принадлежащая только `osago-aggregator`.

Хранилище необходимо по следующим причинам:

1. При десяти страховых компаниях пик в 2 500 одновременных пользователей создаёт до 25 000 параллельных внешних заявок. Состояние такого процесса нельзя надёжно держать только в памяти экземпляра приложения.
2. Каждая страховая компания возвращает собственный идентификатор заявки. Его нужно сопоставить с внутренним `applicationId`.
3. Опрос должен продолжиться после рестарта pod, перевыкладки или перераспределения нагрузки между экземплярами.
4. Несколько экземпляров агрегатора должны координировать получение заданий, чтобы одна и та же внешняя заявка не опрашивалась одновременно разными pod.
5. Для надёжной публикации офферов требуется Transactional Outbox.
6. Для идемпотентной обработки входящих событий требуется Inbox либо уникальный индекс по `eventId`.

Минимальные сущности хранилища:

- `osago_search`: внутренний поиск, `application_id`, `deadline_at`, общий статус;
- `insurer_request`: состояние по каждой страховой компании, внешний `insurer_application_id`, статус, `next_poll_at`, число попыток, lease владельца, последняя ошибка;
- `offer`: полученные предложения;
- `inbox_processed_event`: обработанные входящие события;
- `outbox_event`: события для Kafka.

## 3. API между `core-app` и `osago-aggregator`

`osago-aggregator` не предоставляет `core-app` синхронный бизнес REST API. Он предоставляет асинхронный событийный API через Kafka.

### 3.1. Команда от `core-app`

Топик: `osago-applications.v1`  
Ключ сообщения: `applicationId`  
Событие: `OsagoApplicationRequested`

Основные поля:

- `eventId`;
- `eventVersion`;
- `occurredAt`;
- `applicationId`;
- `clientId`;
- данные автомобиля и водителей в минимально необходимом для страховщиков объёме;
- `requestedInsurerIds`;
- `deadlineAt`.

### 3.2. Результаты от `osago-aggregator`

Топик: `osago-search-events.v1`  
Ключ сообщения: `applicationId`

Типы событий:

- `OsagoOfferReceived`: получено предложение конкретной страховой компании;
- `OsagoInsurerFailed`: страховая компания вернула терминальную ошибку либо недоступна;
- `OsagoSearchCompleted`: все компании завершили обработку либо истекли 60 секунд.

Ключ `applicationId` сохраняет порядок событий одной пользовательской заявки внутри одной партиции. Форматы событий регистрируются в Schema Registry и изменяются обратно совместимо.

### 3.3. Почему выбран Event-Streaming

1. Запрос не блокирует HTTP-поток `core-app` на 60 секунд.
2. Kafka сглаживает кратковременный пик из 2 500 заявок.
3. `osago-aggregator` можно независимо масштабировать по lag топика и количеству ожидающих polling-задач.
4. Офферы поступают в `core-app` по одному, сразу после ответа каждой страховой компании.
5. Отказ или рестарт одного экземпляра не приводит к потере принятой заявки.

## 4. API `core-app` для веб-приложения

### 4.1. Создание поиска

`POST /api/v1/osago/applications`

Заголовок: `Idempotency-Key: <uuid>`

Ответ после сохранения заявки:

```json
{
  "applicationId": "7f0c...",
  "status": "SEARCHING",
  "expiresAt": "2026-07-30T19:00:00Z",
  "streamUrl": "/api/v1/osago/applications/7f0c.../events"
}
```

HTTP-статус: `202 Accepted`. `core-app` не ожидает ответов страховщиков внутри этого запроса.

### 4.2. Поток частичных результатов

`GET /api/v1/osago/applications/{applicationId}/events`

Заголовок ответа: `Content-Type: text/event-stream`

Типы SSE-событий:

- `snapshot`: текущее состояние и уже полученные офферы при подключении или переподключении;
- `offer`: новое предложение;
- `insurer-failed`: ошибка конкретной страховой компании;
- `completed`: поиск завершён;
- `heartbeat`: служебное событие для удержания соединения.

События содержат монотонный `id`. Браузер передаёт `Last-Event-ID` при автоматическом переподключении. Поток завершается после `completed` или по достижении срока 60 секунд.

### 4.3. REST fallback

`GET /api/v1/osago/applications/{applicationId}`

Метод возвращает текущее состояние поиска и все уже сохранённые офферы. Он нужен после потери SSE-соединения, при обновлении страницы и как резервный способ восстановления состояния.

## 5. Интеграция веб-приложения и `core-app`

Используются два средства:

1. REST для создания заявки и чтения текущего состояния.
2. SSE для доставки каждого оффера сразу после его поступления.

SSE выбран вместо WebSocket, потому что в данном сценарии после создания заявки данные передаются преимущественно в одном направлении: от сервера к браузеру. SSE работает поверх обычного HTTP, поддерживает автоматическое переподключение и `Last-Event-ID`, а также проще проходит через прокси и балансировщики.

Для 2 500 одновременных соединений endpoint должен быть неблокирующим. В Spring допустимы WebFlux/Netty либо асинхронный Servlet API. Модель «один занятый поток на одно соединение» использовать не следует.

## 6. Паттерны отказоустойчивости

### 6.1. Веб-приложение → `core-app`

Rate Limiting. На Ingress/API Gateway вводится ограничение частоты создания поисков и количества одновременных SSE-соединений на пользователя. Ограничитель должен учитывать плановую нагрузку, а не блокировать легитимный пик. При исчерпании подтверждённой пропускной способности система должна быстро вернуть `429 Too Many Requests`, а не принимать заявку, которая гарантированно не уложится в 60 секунд.

Повтор `POST` допустим только с тем же `Idempotency-Key`, иначе пользователь может создать дубликаты.

### 6.2. `osago-aggregator` → страховые компании

Паттерны применяются отдельно для каждой страховой компании, чтобы сбой одного контрагента не влиял на остальных.

Rate Limiter. Ограничивает запросы в соответствии с договорным лимитом конкретного страховщика. Создание заявок и polling могут иметь отдельные квоты.

Timeout. Для каждого HTTP-вызова задаются connect timeout и response timeout. Дополнительно действует абсолютный бизнес-deadline `deadlineAt`, равный 60 секундам от начала поиска. После него новые вызовы не выполняются.

Retry. Повторы разрешены только для временных ошибок сети, `408`, `429` с учётом `Retry-After` и части ответов `5xx`. Используется экспоненциальная задержка с jitter, то есть случайным разбросом. `GET` предложения можно повторять безопасно. `POST` создания заявки повторяется только при поддержке страховщиком идемпотентного ключа либо однозначно безопасной семантики. Иначе тайм-аут ответа считается неопределённым результатом и требует отдельной сверки, чтобы не создать дубликат.

Circuit Breaker. Ведётся отдельно по страховой компании и, желательно, по endpoint. При превышении порога ошибок цепь открывается, новые вызовы быстро отклоняются, а в `core-app` отправляется `OsagoInsurerFailed`. Полуоткрытые проверки выполняются ограниченно.

### 6.3. Kafka

Producer использует ограниченные повторы и delivery timeout. Consumer обрабатывает события с семантикой `at-least-once`, поэтому операции идемпотентны. После исчерпания повторов сообщение направляется в DLQ. Circuit Breaker между `core-app` и `osago-aggregator` не требуется, поскольку между ними нет синхронного вызова.

## 7. Учёт нескольких экземпляров сервисов

### 7.1. `osago-aggregator`

- Все экземпляры входят в одну Kafka consumer group `osago-workers`.
- Партиционирование по `applicationId` распределяет пользовательские заявки и сохраняет их порядок.
- Состояние находится в PostgreSQL, а не в памяти pod.
- Polling-задачи распределяются через lease или `FOR UPDATE SKIP LOCKED`.
- Уникальный индекс `(application_id, insurer_id)` и Inbox предотвращают дублирование.
- HPA масштабирует сервис по Kafka lag, числу просроченных `next_poll_at`, активным HTTP-вызовам и загрузке пулов соединений.

### 7.2. `core-app` и SSE

REST-часть остаётся stateless. Однако SSE-соединение физически открыто на одном экземпляре `core-app`, тогда как событие Kafka может обработать другой экземпляр. Поэтому добавляется `SSE Backplane` на Redis Pub/Sub:

1. любой pod `core-app`, обработавший событие, сохраняет его в `core-db`;
2. после commit он публикует короткое уведомление в Redis по каналу `applicationId`;
3. все pod получают уведомление, но отправляет его клиенту только тот pod, на котором открыто соответствующее SSE-соединение.

Redis не является источником истины. Если уведомление потеряно, оффер остаётся в `core-db`; при переподключении клиент получает `snapshot`. Поэтому потеря Pub/Sub-сообщения не означает потерю бизнес-данных. Sticky sessions не обязательны.

## 8. Transactional Outbox

Паттерн применяется в двух местах:

1. `core-app`: сохранение пользовательской заявки и `OsagoApplicationRequested` выполняется в одной транзакции.
2. `osago-aggregator`: сохранение оффера или терминального состояния и соответствующего события выполняется в одной транзакции.

Outbox Relay из задания 3 расширяется на БД `osago-aggregator`. Это предотвращает ситуации «оффер сохранён, но событие не отправлено» и «событие отправлено, но транзакция откатилась».
