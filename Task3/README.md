# Задание 3. Переход InsureTech на Event-Driven архитектуру

## 1. Анализ текущей архитектуры: проблемы и риски

### 1.1. Синхронный fan-out к страховым компаниям

`ins-product-aggregator` формирует ответ только после обращения ко всем страховым компаниям. Время ответа определяется самым медленным внешним API. После подключения ещё пяти страховых компаний число внешних вызовов на один цикл обновления вырастет с пяти до десяти. Это повышает среднюю и хвостовую задержку, вероятность тайм-аутов и количество частичных ошибок.

Риски:

1. Замедление загрузки каталога и зависимых бизнес-операций.
2. Каскадные тайм-ауты и исчерпание пулов потоков и соединений.
3. Отказ одного внешнего API способен сорвать обновление общего списка.
4. Повторные запросы при ошибках увеличивают нагрузку и могут создавать «retry storm», то есть лавину повторов.

### 1.2. Жёсткая временная связанность внутренних сервисов

`core-app` и `ins-comp-settlement` зависят от доступности `ins-product-aggregator` во время выполнения REST-запроса. `ins-comp-settlement` дополнительно зависит от `core-app` при ежедневной выгрузке оформленных страховок.

Риски:

1. Сбой одного сервиса распространяется на зависимые сервисы.
2. Плановые работы или деградация одного компонента нарушают работу всей цепочки.
3. Горизонтальное масштабирование потребителей не устраняет узкое место в синхронном поставщике данных.

### 1.3. Дублирующее и несогласованное опрашивание

`core-app` получает каталог раз в 15 минут, а `ins-comp-settlement` запрашивает его отдельно раз в сутки. Один и тот же набор данных извлекается по разным расписаниям и сохраняется в разных локальных репликах.

Риски:

1. Лишняя нагрузка на `ins-product-aggregator` и внешние API.
2. Разная актуальность данных в сервисах.
3. Отсутствие однозначного ответа, какая версия каталога использовалась при оформлении и взаиморасчёте.
4. Трудности с восстановлением согласованности после пропущенного обновления.

### 1.4. Ежедневная пакетная выгрузка оформленных страховок

`ins-comp-settlement` раз в сутки запрашивает у `core-app` все оформленные за день страховки. С ростом объёма продаж увеличиваются размер ответа, время выполнения запроса, нагрузка на `core-app` и его БД.

Риски:

1. Суточный пик нагрузки и длительные транзакции чтения.
2. Тайм-ауты и необходимость повторной передачи большого набора данных.
3. Потеря записей на границах временного интервала из-за часовых поясов, задержек фиксации или неверного условия выборки.
4. Дублирование данных при повторном запуске задания.
5. Задержка поступления сведений в расчётный сервис до 24 часов.

### 1.5. Отсутствие атомарности между бизнес-транзакцией и передачей события

При простой схеме «сохранить страховку в PostgreSQL, затем отправить сообщение» возможна ошибка между двумя операциями. Обратная последовательность также небезопасна.

Риски:

1. Страховка сохранена, но `ins-comp-settlement` о ней не узнал.
2. Событие отправлено, но транзакция оформления откатилась.
3. Ручная сверка и финансовые расхождения при взаиморасчётах.

### 1.6. Слабая управляемость ошибок внешних интеграций

Текущая синхронная схема чувствительна к нестабильным API страховых компаний. При увеличении числа интеграций растёт вероятность, что хотя бы один контрагент будет недоступен или отвечать медленно.

Риски:

1. Накопление запросов и исчерпание ресурсов приложения.
2. Невозможность изолировать проблемного контрагента.
3. Публикация неполного каталога без признака его качества и времени актуальности.

### 1.7. Недостаточная наблюдаемость

Из исходного описания видно, что команда узнаёт о недоступности приложения от пользователей. Для потоковой архитектуры дополнительно критичны задержка потребителей, размер очереди необработанных событий и состояние outbox.

Риски:

1. Позднее обнаружение отказа.
2. Незаметное отставание локальных реплик.
3. Накопление сообщений в DLQ, то есть очереди сообщений, которые не удалось обработать.
4. Невозможность быстро определить источник задержки: внешнее API, producer, broker или consumer.

### 1.8. Инфраструктурные точки единого отказа

Все приложения работают в одной зоне доступности, а PostgreSQL развёрнут на одной ВМ в единственном экземпляре. Добавление брокера сообщений без высокой доступности создаст ещё одну точку отказа.

Риски:

1. Отказ зоны делает недоступной всю систему.
2. Отказ PostgreSQL останавливает оформление и обновление реплик.
3. Потеря брокера прерывает доставку событий и увеличивает разрыв данных.

### 1.9. Риски, возникающие после перехода на Event-Streaming

Event-Streaming снижает временную связанность, но вводит новые требования:

1. Eventual consistency, или согласованность с задержкой: локальная реплика обновляется не мгновенно.
2. Повторная доставка: семантика должна быть `at-least-once`, а потребители должны быть идемпотентными.
3. Нарушение порядка между партициями: порядок гарантируется только внутри одной партиции.
4. Эволюция схем событий: изменения должны быть обратно совместимыми.
5. Безопасный replay: повторное чтение истории не должно повторно создавать финансовые операции.
6. Защита персональных данных: в события следует помещать только минимально необходимые данные.

## 2. Предлагаемая Event-Driven архитектура

Декомпозиция бизнес-функций не изменяется. Сохраняются `core-app`, `client-info`, `ins-product-aggregator` и `ins-comp-settlement`. Добавляются только инфраструктурные контейнеры: платформа Event-Streaming, outbox-relay и хранилище снимка каталога для агрегатора.

### 2.1. Взаимодействия, переводимые на Event-Streaming

#### Поток A. Обновления продуктов и тарифов

1. `ins-product-aggregator` по расписанию параллельно запрашивает API страховых компаний.
2. Для каждого внешнего API применяются тайм-аут, ограниченное число повторов с экспоненциальной задержкой, circuit breaker и bulkhead. Circuit breaker временно прекращает вызовы нестабильного API, а bulkhead изолирует ресурсы каждой интеграции.
3. Агрегатор нормализует данные и в одной транзакции сохраняет новый снимок каталога и запись в outbox.
4. Outbox-relay через CDC, то есть захват изменений в журнале PostgreSQL, публикует событие в Kafka.
5. `core-app` и `ins-comp-settlement` читают события независимыми consumer group и обновляют собственные локальные реплики.
6. При недоступности отдельной страховой компании сохраняется последняя успешная версия её данных с полями `sourceUpdatedAt`, `receivedAt` и `status`. Ошибка одного контрагента не блокирует обновление остальных.

Рекомендуемый топик: `insurance-products.v1`.

Рекомендуемый формат ключа: `insuranceCompanyId:productId`. Топик следует сделать compacted, чтобы Kafka сохраняла последнюю версию по каждому ключу и позволяла восстановить локальную реплику посредством replay.

#### Поток B. Оформленные страховки

1. `core-app` оформляет страховку и в той же транзакции записывает событие в outbox.
2. Outbox-relay публикует событие `PolicyIssued` в Kafka.
3. `ins-comp-settlement` получает событие сразу после оформления и сохраняет данные в своей БД.
4. Ежедневный REST-запрос из `ins-comp-settlement` в `core-app` удаляется.
5. Месячный реестр формируется из локальной БД расчётного сервиса.

Рекомендуемый топик: `policies-issued.v1`.

Рекомендуемый ключ: `policyId`. Событие должно содержать `eventId`, `eventType`, `eventVersion`, `occurredAt`, `policyId`, `insuranceCompanyId`, `productId`, `tariffVersion`, сумму и валюту, а также минимально необходимый набор расчётных атрибутов. Полные паспортные и контактные данные в событие включать не следует.

### 2.2. Взаимодействия, которые остаются синхронными

1. Веб-приложение и партнёры обращаются к `core-app` по REST, поскольку им требуется немедленный результат команды или запроса.
2. `core-app` обращается к `client-info` при проверке и изменении клиентских данных, необходимых для текущего оформления.
3. `ins-product-aggregator` обращается к API страховых компаний по REST, SOAP или GraphQL, поскольку внешние системы не предоставляют поток событий.
4. Вызовы платёжного сервиса остаются синхронными в рамках пользовательского сценария.
5. Передача месячного реестра страховым компаниям остаётся отдельной интеграционной операцией `ins-comp-settlement`.

## 3. Решение по паттерну Transactional Outbox

Transactional Outbox необходимо использовать.

### 3.1. Где применяется

1. В `core-app`: запись оформленной страховки и события `PolicyIssued` выполняется в одной транзакции PostgreSQL.
2. В `ins-product-aggregator`: запись новой версии каталога и события об обновлении выполняется в одной транзакции PostgreSQL.

### 3.2. Как доставляются события

Outbox-relay реализуется через Debezium или аналогичный CDC-коннектор. Он читает изменения таблиц outbox из журнала транзакций PostgreSQL и публикует их в Kafka. После успешной публикации записи очищаются по политике хранения или помечаются обработанными.

### 3.3. Гарантии доставки

Не следует заявлять сквозную гарантию `exactly-once`. Практичная модель:

1. `at-least-once` между outbox и потребителем;
2. уникальный `eventId`;
3. таблица `inbox_processed_events` или уникальное ограничение на `eventId` у потребителя;
4. атомарная транзакция «проверить eventId, обновить локальные данные, отметить событие обработанным»;
5. повторная обработка не меняет результат.

## 4. Требования к брокеру и эксплуатации

1. Kafka разворачивается как кластер минимум из трёх брокеров в нескольких зонах доступности с replication factor 3.
2. Для каждого потока создаются отдельные consumer group: `core-product-replica` и `settlement-data-projection`.
3. Ошибки обработки после ограниченного числа повторов направляются в DLQ.
4. Схемы событий регистрируются в Schema Registry и изменяются обратно совместимо.
5. Контролируются метрики: consumer lag, возраст последнего обновления каталога, размер outbox, число повторов, DLQ, задержки и ошибки API каждой страховой компании.
6. Настраиваются алерты на отсутствие событий, рост lag, накопление outbox и превышение допустимого возраста данных.
7. Производители и потребители масштабируются горизонтально. Число партиций выбирается по нагрузочному тесту и требуемому параллелизму.
8. PostgreSQL переводится с одиночной ВМ на отказоустойчивую конфигурацию с резервной репликой, автоматическим failover и проверяемыми резервными копиями.

## 5. Ожидаемый результат

1. `core-app` и `ins-comp-settlement` перестают синхронно опрашивать `ins-product-aggregator`.
2. `ins-comp-settlement` перестаёт ежедневно выгружать оформленные страховки из `core-app`.
3. Рост числа страховых компаний не увеличивает время ответа внутренних потребителей.
4. Ошибка одного внешнего API изолируется и не блокирует весь каталог.
5. Локальные реплики можно восстановить повторным чтением событий.
6. Сведения об оформленной страховке не теряются между PostgreSQL и Kafka.
7. Состояние потоков становится наблюдаемым через lag, outbox и DLQ.
